Oasis 2.4.0 (222): concrete Dart AOT lighting commands
2026-10-11. STATIC ONLY; no application execution or hardware access.

RESULTS
The following are decrypted Bluetooth Mesh ACCESS PDUs, NOT GATT payloads.
Use the configured AppKey, vendor model 0x02E5C00A, and a valid mesh destination.
Native code uses company 0x02E5, model 0xC00A, opcode=(messageId>>16)&0x3f.
It emits [0xc0|opcode, 0xe5, 0x02] followed by these unchanged payload bytes.

Command       messageId   Complete access PDU
Off           0xC3E502    C3 E5 02 00
On            0xC3E502    C3 E5 02 01
Brightness    0xC4E502    C4 E5 02 || brightness_u8 || LE32(epoch_seconds)
Temperature   0xC5E502    C5 E5 02 || LE16(kelvin)
RGB color     0xC6E502    C6 E5 02 || red_u8 || green_u8 || blue_u8
Color mode    0xCCE502    CC E5 02 01
White mode    0xCCE502    CC E5 02 02
Combined      0xD2E502    D2 E5 02 || LE16(kelvin) || brightness_u8
                                    || LE32(epoch_milliseconds & 0xffffffff)

No extra TID, transition time, or checksum is appended by these builders.
The device wrapper supplies acknowledged=false. Native wrapper also defaults
acknowledged=false. It encrypts/frames through Nordic mesh before proxy GATT.
Brightness/temperature fields are masked to bytes, not scaled in these builders.
The app's diagnostic combined caller generates brightness 0..100 and temperatures
2700..6500; this is caller evidence, not proof of the firmware's accepted limits.
Runtime acceptance/physical light response must be verified by the main agent.

RGB FOLLOW-UP: CONCRETE ORDER AND PURE-RED PDU
  Pure red: C6 E5 02 FF 00 00. No timestamp/TID/brightness byte.
  Room color path0x8cb8b0 allocates INa at0x8cb910 via stub0x8cb990;
  allocation tags0x48f11c prove cid1167. It stores the color object at+7
  (0x8cb91c), then calls room routing0x8525a4 at0x8cb930.
  Dispatch mapping resolves ID getter0x6f942c and payload getter0x7060e0.
  ID getter MOV #0xe502 + MOVK #0xc6,lsl16 =>0xC6E502 unboxed.
  Builder calls helpers in this order:
    0x706108 ->0x2eed40 (red); 0x706114 ->0x2eec78 (green);
    0x706120 ->0x2eebb0 (blue).
  Saves results, stores array elements in that same order at0x706160,
  0x70617c,0x706198; copies exactly3 bytes at0x7061cc/0x7061d8.
  Independent executable mapping of helper semantics:
    serializer0x2ee4d4 writes key red then calls0x2eed40 at0x2ee5dc,
    key green then0x2eec78 at0x2ee638,
    key blue then0x2eebb0 at0x2ee694, storing each result under that key.
  Serializer0x7f2ca0 repeats the same mapping from object field+7.
  Helpers dispatch normalized color channels, multiply by double255
  (pool0x3e60 bits0x406fe00000000000), round through runtime helper,
  and return integers. For pure endpoints0.0/1.0 this yields0/255 exactly.
  This is a static command-format result, NOT proof that ambient_2_0 firmware
  implements RGB or that color changes preserve previously set brightness.
  No further hardware action was taken by this worker.

EXAMPLE COMBINED VALUE DERIVATION
  6500 decimal =0x1964 => LE16 bytes64 19.
  100 decimal =0x64 => brightness byte64.
  Therefore prefix D2 E5 02 64 19 64 is correct, followed by low32
  epoch-milliseconds in little-endian order (total access length10).

MODE FOLLOW-UP AFTER MAIN REPORTED GREEN DID NOT VISIBLY CHANGE THE LAMP
  Evidence-backed color-mode command: CC E5 02 01.
  Evidence-backed white/temperature-mode command: CC E5 02 02.
  Green remains C6 E5 02 00 FF 00; its format is separate from mode switching.
  Physical failure of C6 alone must be recorded; it is not proof of CCT-only
  hardware. Nor does finding these commands prove firmware RGB support.
  Mode-selector callback0x5b36b8 selects pool0x5a78 for temperature or
  pool0x35a90 for color, then calls0x5b3718 ->0x5736fc ->0x8cac90.
  0x8cacf0 allocates JNa via0x851fb0, tags0x48e11c =>cid1166.
  Stores enum field+7 at0x8cacfc; sends via0x8525a4 at0x8cad10.
  Dispatch resolves ID0x6f9438=>0xCCE502, payload0x7061f4.
  Builder loads enum from command+7 then unboxed int64 at enum+0x13
  (actual object offset0x14), returns exactly one byte.
  Task-local dae diagnostic OASIS_ENUM_EVIDENCE dumps snapshot instances:
    ref0x12402 (temperature): slots [unboxed1,unboxed0,name,unboxed2,unboxed0]
    ref0x12403 (color):       slots [unboxed0,unboxed0,name,unboxed1,unboxed0]
  Compressed slots are4 bytes starting at object offset8; slots3/4 form the
  64-bit value at0x14: temperature2, color1. These are NOT enum ordinal values.
  Independent white-mode call0x84f35c allocates JNa, loads temperature enum
  at0x84f364, sends at0x84f37c, then logs "Sent white mode command".
  RGB routine0x8cb8b0 only sends INa/C6, then sets its LOCAL cached mode to
  color at0x8cb974. It does not also transmit JNa/CC or ON in this routine.
  A mode switch followed by RGB is therefore an evidence-backed next test;
  its success has not been observed by this static-only worker.

STATE READBACK: NEGATIVE EVIDENCE / BOUNDARIES
  No verified power/brightness/CCT/RGB query+status schema has been recovered.
  Native vk/e registers vk/p as MeshStatusCallbacks (vk_e.txt offset0x1d4).
  vk/p.onMeshMessageReceived explicitly handles composition, app-key, model
  binding and subscription statuses, a missing-data transfer response, and
  WiFi/provisioning response handling. Its terminal vendor fallback logs
  "Unhandled message opCode" (offset0xbba..0xc30), without forwarding a
  generic vendor state payload to Dart. onUnknownPduReceived also only logs.
  The examined handlers do not decode lighting-state fields from vendor PDUs.
  Thus transport/configuration response is NOT evidence of light-state readback.
  App RGB/mode routines update local model fields after command dispatch; these
  writes are not physical-state acknowledgements. UI state can be optimistic.
  An empty-payload command class1171/ENa also shares messageId0xCCE502,
  but its semantics are NOT established; do NOT label/send it as a state query
  based on empty payload alone. Firmware may expose queries unused by this app.

PROVISIONING DEPENDENCY
analysis/native/vk_p.txt, static-OOB callback, offsets0x8c..0x108:
  reads vk/j.f (nodeId); UTF-8 encodes it; allocates32 zero bytes;
  copies min(nodeId byte length,32); converts to hex and calls
  MeshManagerApi.setProvisioningAuthentication.
If static OOB is requested but nodeId missing/empty, actual control flow fails
with "Static OOB data requested but nodeId not available". An earlier log
claims no-OOB fallback, but does not describe the executed error path.
This establishes app preparation of OOB; final algorithm-dependent consumption
inside Nordic provisioning has not been fully traced here.
No reset/provisioning is required merely to use an already authenticated mesh.
